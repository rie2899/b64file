## 二、P1：大文件 Web Worker

**现状**：`src/tool.ts` 的 `encodeBytesToBase64`（分块 String.fromCharCode + btoa）和 `decodeBase64ToBytes`（atob）都跑在主线程。100 MB 文件编码时页面冻结数秒；20 MB 确认弹窗只是提醒，不解决卡顿。

**影响**：真实用户贴大 PDF/图片时 UI 无响应，看起来像挂了。这是唯一影响核心功能的未完成项。

**方案要点**：新建 worker 模块（Vite `?worker` 导入），>20 MB 自动走 worker 路径，进度可反馈「编码中…」；结果字符串用 transferable 传回。改动集中在 tool.ts + 新 worker 文件，测试可保留（worker 逻辑可拆纯函数复测）。

**边界要诚实**：Worker 解决的是「卡 UI」，不解决内存——100 MB 文件编码峰值内存仍是数百 MB 级，这是浏览器 Base64 的物理限制，弹窗提醒仍然需要。

**工作量**：半天。**风险**：低。
